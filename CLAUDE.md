# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Scope and ownership

Everything in this workspace is first-party software owned and operated by JES LLC: the `pidgeiot` backend and dashboard, the sibling `pigeon` Zephyr device library, the sibling `loft` CoAP terminator, and the services they run on (Cloudflare account, VPS, Postgres cluster, and the development hardware on the bench). Work here is ordinary product engineering on our own systems — building device authentication, reviewing our own code for correctness before we deploy it, and provisioning our own devices and staging environments. There is no third-party system in scope and no third-party data involved.

Because the product is an IoT platform, much of the code is about credentials by nature: device keypairs, pre-shared keys, session cookies, bearer tokens. Reviewing that code for robustness, validating untrusted network input, and bounding resource use on public listeners are all defensive engineering tasks on our own service.

Handling rule that follows from this: credential *values* — anything in `secrets.env`, device tokens, database connection strings, private keys under `app/keys/`, minted PSKs — are never printed, echoed, or written into files, commits, or chat. Reference them by name and read them from the environment. Production deploys, `cargo publish`, and `git push` are gated on explicit approval from the repo owner each time.

## Project overview

PidgeIoT is an edge-native IoT platform built in Rust, structured as a Cargo workspace with three crates:

- **`dovecote`** (backend): serverless edge router on Cloudflare Workers + Durable Objects. Compiles to a `cdylib` via `worker-build`. Handles device ingestion, provisioning, and session validation.
- **`fancier`** (frontend): WebAssembly SPA built with Dioxus 0.7 + TailwindCSS/DaisyUI. The human-facing dashboard.
- **`capsules`** (shared models): serde structs/RPC schemas shared by both `dovecote` and `fancier` so frontend/backend stay in sync. Keep this crate free of Worker- or Dioxus-specific dependencies.

`loft`, the CoAP/DTLS terminator that fronts the device routes from the VPS, used to be a fourth crate here and now lives in its own repo (`github.com/justins-engineering/loft`, cloned at `~/loft`) along with its FFI shims, its CID regression harness, and its deployment runbook (`docs/infra/coap-terminator.md` and `docs/infra/coap-cid-design.md` moved with it; that repo's README is the way in). The seam between the two is `docs/api.md`: dovecote's `GET /internal/coap-psk/:pigeon_id` and the `/device/pigeons/:id/*` routes loft proxies onto. `capsules::CoapPskLookup` is dovecote's half of that first contract; loft carries its own copy of the same wire shape, so changing either side means changing both repos.

Auth/identity is handled by a self-hosted Ory Kratos instance for dashboard users (dev: `docker-compose.yml`; production since 2026-08-23: the native `kratos` v26.2.0 binary under systemd on a small VPS — unit `/etc/systemd/system/kratos.service` (ships in-repo at `infra/systemd/kratos.service`), binary `/usr/local/bin/kratos`, `DSN` and `COURIER_SMTP_CONNECTION_URI` loaded from the root-only 0600 `/opt/kratos/.env`, binding `127.0.0.1:4433`/`:4434` on loopback so the only route in is the host `INPUT` chain, published as `auth.pidgeiot.com` through a Cloudflare Tunnel that needed no change; the superseded `oryd/kratos:v26.2.0` container is stopped with `--restart=no` and left on disk as the rollback path, so the docker daemon is no longer in the auth path at all — procedure, verification and rollback in `docs/infra/kratos-systemd-migration.md`; config/bring-up live in the gitignored `.migration/`, secrets in the gitignored `secrets.env`), plus per-pigeon Ed25519 keypairs and compact binary bearer tokens (not JWTs) for device auth — see `dovecote` below. **Three hard-won Kratos production gotchas (task #47 cutover):** (0) Kratos MUST be invoked as `serve ... --watch-courier` (now the systemd unit's `ExecStart`) — without that flag a single-instance Kratos silently QUEUES all outbound mail (`courier_messages` rows stuck at status 1, `send_count` 0, nothing ever reaches the SMTP provider, no error anywhere) — dev's docker-compose always had it; the first VPS bring-up didn't, which broke signup verification emails until the live launch test caught it; (1) the prod config MUST keep `cookies.domain: pidgeiot.com` — without it the session cookie is host-only to `auth.pidgeiot.com`, the browser never sends it to `api.pidgeiot.com`, dovecote's whoami 401s, and every dashboard list silently renders empty; (2) importing identities through the Kratos admin API mints NEW identity UUIDs — since `flocks.user_id` and each DO-resident `pigeon_acl` key on the original IDs, any future identity move must preserve IDs (see `.migration/remap2.sql` for the deferrable-FK in-place restore pattern; managed Postgres owner roles can't `DISABLE TRIGGER ALL`).

Full HTTP API reference (every dashboard + device route, auth models, request/response shapes): `docs/api.md`.

## Architecture

### `dovecote` — edge router + Durable Objects

- `src/lib.rs` — the single Cloudflare Worker entrypoint (`#[event(fetch, ...)]`). Defines all HTTP routes on a `worker::Router`. Every route handler manually attaches CORS via `.with_cors(&cors)` and returns explicit error `Response`s (no `?`-propagation through route closures — see git history: "Unroll router let chains to avoid silent failures", "Response::Error() can't fail, unwrap instead of ?"). When adding routes, follow the existing pattern of `let Ok(x) = ... else { return Response::error(...) }` rather than `?`.
- CORS is **not** a global static — each route closure calls `build_cors(&ctx.env, &req)` itself (`lib.rs`), matching the request's `Origin` header against `ROOT_URL` and handing `Cors::with_origins` exactly that one matching value (or `ROOT_URL` as an inert non-matching default). This exists because `worker::Cors` joins every configured origin into `Access-Control-Allow-Origin` with commas rather than matching per-request — a comma-joined value is invalid per the CORS spec and real browsers silently reject it once more than one origin is configured, so a single shared multi-origin `Cors` can't be used here. It also can't be computed once in `main` and shared by reference across routes, since each route is a separate `async move` closure and `Cors` isn't `Copy`. `ROOT_URL` (`[vars]`/`[env.dev.vars]`, `wrangler.toml`) is the frontend's own origin in both environments — `https://pidgeiot.com` in production, the local `dx serve` address in dev.
- Two local macros in `lib.rs` remove boilerplate: `get_pigeon_do!` (resolves `pigeon_id` → Durable Object stub) and `get_db!` (opens a Postgres client via Hyperdrive, mapping failure to a 500). Both take the caller's local `cors` as a final `$cors:expr` argument (needed for their early-return error paths) since macro hygiene means they can't see a caller-scope `cors` implicitly.
- **Dual persistence model**: each `Pigeon` is authoritative in its own Durable Object (SQLite-backed, one row per DO), and is also mirrored into Postgres (via Cloudflare Hyperdrive) for cross-pigeon querying (e.g. listing a flock's pigeons). The DO is the source of truth; every mutating route proxies to the DO first, then best-effort syncs the result to Postgres (`update_pigeon_pg_db`, `insert_pigeon_pg_db`, etc. in `src/helpers/pigeons.rs`) — a Postgres sync failure is logged but does not fail the request.
- `src/objects/pigeons.rs` — the `Pigeons` Durable Object. Owns its own embedded SQLite schema (created in `DurableObject::new`, mirrors `init-db.sql`'s Postgres schema but with SQLite triggers for `updated_at`/immutability/shadow version bumping). Internal routes are dispatched by string path match (`/pigeon/get`, `/pigeon/create`, `/pigeon/shadow/update`, etc.) and are reached only via `proxy_to_pigeon_do` from the top-level router — never exposed directly to the internet.
- Authorization inside the DO is header-based, not cookie-based, for user-facing routes: the router resolves the Kratos session into a user id and forwards it as `X-User-Id`; `is_authorized`/`is_owner` in `objects/pigeons.rs` check that header against the DO's local `pigeon_acl` table. The device-facing route (`GET /device/pigeons/:id/shadow`, dispatched inside the DO as `/pigeon/device/shadow`) does **not** go through `X-User-Id`/ACL at all — a device has no Kratos user identity. Instead `get_shadow_device` (`objects/pigeons.rs`) verifies the request's `Authorization` bearer token directly against this pigeon's own `device_public_key` column, via `verify_device_token` (`objects/helpers.rs`). This used to be gated by a `X-User-Id: ""` sentinel that `is_authorized` had no special case for, permanently 403ing the route — replacing ACL-based auth with real per-pigeon cryptographic auth for this route removed the need for that sentinel entirely.
- Device auth mechanism (`src/objects/helpers.rs`, `src/objects/pigeons.rs`) — **not JWT**: each pigeon gets its own Ed25519 keypair, generated fresh in the DO on `create` and on `token/refresh` (`mint_device_credential`). Only the public key is ever persisted (in the DO's own SQLite `pigeons.device_public_key` column — never mirrored to Postgres, never returned over the API); the private key signs one token and is discarded. The token itself is a 69-byte binary blob — `version(1) | expires_at(4, u32 LE unix seconds) | signature(64)` — base64url-encoded for transport, with no `pigeon_id`/subject claim: the binding to a specific pigeon comes from which pigeon's stored public key the DO verifies against, not from a claim inside the token. There are no `DEVICE_SEED`/`DEVICE_PUBLIC_KEY` Worker secrets anymore — verification happens entirely inside the owning DO (`verify_device_token`), reached via `proxy_to_pigeon_do` forwarding the caller's `Authorization` header straight through (`src/helpers/pigeons.rs`). **Refreshing a device's token revokes the previous one**: `refresh_token` mints a brand-new keypair and overwrites `device_public_key`, so the old token's signature can never verify again, regardless of its embedded expiry.
- `src/helpers/auth.rs` now holds only `authenticate_browser` (Kratos session cookie validation for dashboard users).
- **Device-facing shadow report-back and telemetry ingestion** (`objects/pigeons.rs`, added 2026-07-15): both share device auth via `is_authorized_device()` (factored out of what used to be three near-identical checks duplicated across `get_shadow_device`/`report_shadow_device`/`report_telemetry_device` — bearer token vs. this pigeon's own `device_public_key`, no ACL). `POST /device/pigeons/:id/shadow` → DO-internal `/pigeon/device/shadow/report` → `report_shadow_device`: a device confirms it applied `target_config` by writing its own `current_config`/`current_version` into `pigeon_shadow`; like the dashboard's `PUT /pigeons/:id/shadow`, the gateway route also best-effort syncs the result to Postgres via the existing `update_shadow_pg_db`, so Postgres's mirrored shadow state doesn't go stale for pigeons that report back on their own. `POST /device/pigeons/:id/telemetry` → DO-internal `/pigeon/device/telemetry` → `report_telemetry_device`: body is a flat JSON object of string key/value pairs, upserted one row per key into the DO's `pigeon_telemetry` table (`key` `PRIMARY KEY`, `value`, `reported_at`) — latest-value-per-key, not a time-series log; `GET /pigeons/:id/telemetry` (dashboard) reads it straight through the DO (route has no `/latest` suffix — `docs/api.md` is the authority; a stale `/latest` mention here previously misled a hardware-verification pass).
- **Telemetry history + user-definable forwarding endpoint** (added 2026-07-17, `queue.rs` + `helpers/telemetry.rs`): telemetry writes ride a Cloudflare Queue (`pidgeiot-telemetry`, per-env producer/consumer split in `wrangler.toml` — a plain `wrangler deploy`, not `versions upload`, is required to actually register a consumer). The consumer reads the DO's `TelemetryWriteResult` and picks one of two paths per-pigeon: if the pigeon has no `telemetry_endpoint` configured, best-effort write into Postgres `pigeon_telemetry_history` (queryable via `GET /pigeons/:id/telemetry/history` and the flock-wide variant, `query_telemetry_history_for_pigeon`/`_for_flock` in `helpers/telemetry.rs`); if one *is* configured (`PUT`-able via `update_telemetry_endpoint_pg_db`/the `telemetry_endpoint` column, `PigeonTelemetryEndpointUpdateRequest` in `capsules`), forward instead as InfluxDB line protocol v2 (GreptimeDB-compatible) via `forward_line_protocol` — the two paths are mutually exclusive per report, not both. `auth_token` on a configured endpoint is stripped on reads, same convention as connector tokens. Non-numeric telemetry values are stored/history'd but intentionally excluded from line-protocol forwarding (they'd emit invalid lines) and don't appear in `fancier`'s graphable-key picker.
- **Device dictionary-log ingestion** (added 2026-07-17, `objects/pigeons.rs`): `POST /device/pigeons/:id/logs` (device-auth'd, `is_authorized_device()`, capped at `capsules::MAX_LOG_CHUNK_BYTES` = 16KiB per chunk) appends into a 200-chunk DO-local ring buffer (`PigeonLogChunk`/`PigeonLogChunkRow` in `capsules`, base64-stored since chunks are opaque binary — Zephyr `CONFIG_LOG_DICTIONARY_SUPPORT` dictionary-encoded logs, not plaintext); `GET /pigeons/:id/logs` (dashboard-auth'd) returns the buffer as base64 for client-side decode. No Postgres mirror (DO-local ring buffer only, by design — this is a rolling debug buffer, not a durable log store). Binary (non-UTF-8) device request bodies are proxied to the DO via `proxy_binary_to_pigeon_do` (`helpers/pigeons.rs`), distinct from the JSON-only `proxy_to_pigeon_do`.
- **Firmware storage + FOTA** (added 2026-07-18, task #23): per-flock firmware catalog in Postgres (`init-db.sql`) plus content-addressed image bytes in R2 (`pidgeiot-firmware`/`-staging` buckets, per-env bindings in `wrangler.toml`). `capsules::FirmwareTarget`/`FirmwareImage`/`FirmwareUploadQuery` (+ `MAX_FIRMWARE_BYTES`) define the catalog shape; a pigeon's shadow `target_config` can embed a `firmware` key (`FirmwareTarget`: version string + expected size + sha256) that a device diffs against its own running version to decide whether to start a download — the shadow PUT from the dashboard replaces `target_config` wholesale, so `fancier`'s `merge_firmware_target` helper exists specifically to patch just that key in without clobbering `log`/`telemetry_interval`/`reboot`. Device download is `GET /device/pigeons/:id/firmware/:version` (device-auth'd), HTTP Range-aware (chunked download, matches `pigeon`'s FOTA client) — dovecote streams straight from R2, sha256 isn't re-verified server-side per chunk (the device verifies the full image after assembly). Known gotcha (found via real hardware e2e, 2026-07-20): an R2-stored FOTA test/staging image is a separately-built-and-signed artifact from whatever's currently flashed as the "primary" image — if a device's token gets rotated *after* a test firmware image was built, that image still carries the stale token baked in via `CONFIG_PIGEON_TOKEN`, and will 401 on every request once booted into, even though the FOTA mechanism itself worked correctly. Any OTA test image needs rebuilding (not just re-uploading) after a token rotation.
- **WebSocket device endpoint** (added 2026-07-19, task #32, `objects/ws.rs` + `objects/pigeons.rs`): `GET /device/pigeons/:id/ws` (gateway route checks `Upgrade: websocket`, proxies via `proxy_websocket_to_pigeon_do` in `helpers/pigeons.rs`) accepts a persistent channel for non-cellular devices as an alternative to polling HTTPS. Uses the Durable Object **Hibernation API** (`State::accept_websocket_with_tags`, `get_websockets_with_tag`, `WebSocket::serialize_attachment`/`deserialize_attachment`, `DurableObject::websocket_message`/`_close`/`_error` — confirmed present in the `worker` crate v0.8.5) so an idle connection survives DO eviction without keeping the DO warm. Gated by `is_authorized_device()` before accept, same as the device HTTPS routes; one socket per pigeon enforced via the tagged `get_websockets_with_tag` lookup. Frame protocol (`objects/ws.rs`) handles `telemetry`/`shadow_report`/`ping` frames from the device, and the DO broadcasts a `shadow_update` frame over any open socket whenever the dashboard writes a new shadow — so a WS-connected device can react to config pushes without polling. Full frame shapes documented in `docs/api.md`. **Device-side client landed 2026-07-20 (task #33)** — `pigeon`'s `CONFIG_PIGEON_WS` client + `pigeon-examples` `wifi_init` sample, hardware-verified end-to-end on a real ESP32-C6 against `dovecote-staging` (WS connect, `shadow_update` push applied ~1s after a dashboard PUT, telemetry-over-WS, HTTPS fallback, and socket-steal reconnect/one-socket-per-pigeon recovery all confirmed on-device). See `~/pigeon`/`~/pigeon-examples` CLAUDE.md for the device side. Backend WS endpoint **promoted to prod 2026-07-22** — the same staging-verified `dovecote` binary is now deployed to production (`api.pidgeiot.com`); the WS gateway route responds and gates there. The remaining belt-and-suspenders check is a real device connecting over WS to `api.pidgeiot.com` (the device-side client was hardware-verified end-to-end against `dovecote-staging`, and prod runs the identical code).
- Connectors: a `Pigeon` has one `Connector` (`Https` or `Coap`), each carrying its own endpoint + token/PSK. Tokens are always stripped before returning a `Pigeon` from `GET` routes (`objects/pigeons.rs::get`/`get_detail`) — they're only ever returned on `create` or `token/refresh`. The CoAP connector is terminated by `loft` on BOTH transports — CoAP-over-DTLS/UDP (`coaps://`, RFC 7252, the primary device transport) and CoAP-over-TLS/TCP (`coaps+tcp://`, RFC 8323) — on one authority (`COAP_DEVICE_HOST`, port 5684). `build_coap_endpoint` (`objects/pigeons.rs`) mints the `coaps://` (DTLS/UDP) form: the sibling `~/pigeon` Zephyr device library validates the endpoint scheme against its compiled transport and fails loudly on a mismatch, so the stored default must name the primary transport; a TLS/TCP device build keeps the same authority and swaps the scheme to `coaps+tcp://`. `capsules::CoapConfig`'s PSK fields are named `tls_psk_identity`/`tls_psk_secret` — TLS-PSK naming that covers both handshakes.
- Pigeon deletion (`delete` in `objects/pigeons.rs`, dispatched at `/pigeon/delete`, gated by `is_owner`) wipes the DO's own tables — `pigeon_acl` explicitly (it has no FK to `pigeons`, since each DO holds exactly one pigeon's ACL) and `pigeons` itself (`pigeon_shadow` cascades via `ON DELETE CASCADE`). Durable Objects have no "delete yourself" API; emptying its storage is the idiomatic equivalent. The gateway's `DELETE /pigeons/:pigeon_id` route already proxied here and synced the deletion to Postgres before this handler existed — it just 404'd with nothing to dispatch to.
- **Gotcha**: `SqlCursor::one()` (`worker` crate) throws an uncaught JS exception — crashing the DO, not a catchable `Result::Err` — when a query returns zero rows. Every handler in `objects/pigeons.rs` used to assume the `pigeons`/`pigeon_shadow` tables always have exactly one row, which was safe only because nothing could ever leave them empty before `delete()` existed. Use `to_array()` and take the first element instead (see `one_row` in `objects/pigeons.rs`) for any query that could plausibly run against an already-deleted pigeon's DO — plain `.one()` is only safe immediately after an `INSERT ... RETURNING` in the same request.
- `wrangler.toml` defines three environments: default (production, `api.pidgeiot.com`), `[env.staging]` (workers.dev), and `[env.dev]` (local, `127.0.0.1`, using `localConnectionString` for Hyperdrive instead of the shared binding id). **Since 2026-07-26 (task #47) the Hyperdrive origin for prod + staging is a managed Crunchy Bridge PostgreSQL instance** (connection string in the gitignored `secrets.env` as `DOVECOTE_PSQL_CONNECTION`; Kratos's own DB lives on the same Crunchy instance as `KRATOS_PSQL_CONNECTION`), replacing the home-lab single-node YugabyteDB — see `docs/infra/immediate-production-hosting.md` and `docs/infra/postgres-consolidation.md` for the decision trail. In the same migration, **GreptimeDB was retired from prod + staging** (`GREPTIMEDB_ENDPOINT = ""` in both env blocks): telemetry history writes/reads use the designed Postgres `pigeon_telemetry_history` fallback everywhere deployed; only `[env.dev]` still points at the local docker-compose GreptimeDB. Per-pigeon InfluxDB-line-protocol forwarding (`telemetry_endpoint`) is unaffected.
- **Hyperdrive has no caching config, so it runs the default ~60s query cache — this breaks read-after-write verification.** An identical `SELECT` issued *before* a write keeps being served from cache afterwards, so a freshly committed row stays invisible for up to a minute (observed: ~90s for a firmware catalog upload whose `uploaded_at` proved it landed instantly). The natural verify pattern — list, write, list again — is precisely the one that poisons its own check, since the "before" call seeds the cache. This is *database*-query caching, not edge caching: there's no `cf-cache-status` on these responses and a cache-busting query param does nothing. Never re-issue a write on the strength of a stale read; wait >75s or verify with a different query shape. It matters most for the firmware catalog, which has **no delete route** — a retry under a different version label creates a permanent second row needing direct Postgres + R2 surgery.

### `capsules` — shared models

Plain serde structs with no Worker/Dioxus dependencies, consumed by both other crates via `capsules.workspace = true`. Notable pattern: every entity has a `*Row` variant (deserializes DB-native types, e.g. unix-epoch floats/integers for timestamps) and a public API variant (RFC 3339 `OffsetDateTime`), connected by a `From<XRow> for X` impl. When adding a new persisted field, update both variants and the conversion.

### `fancier` — Dioxus SPA

- `src/lib.rs` defines the full route table (`Route` enum, `Routable` derive) and the top-level `App` component. Routes under `#[layout(Wrapper)] #[layout(AuthGuard)]` require an authenticated Kratos session (checked client-side via `session_cookie_valid()` against `SESSION_COOKIE_NAME`); everything else (login, registration, marketing pages) is public.
- Global reactive state is plain Dioxus `Signal`s provided via context, not a store library: `Session { state: Signal<AuthState> }` for auth, `LocalSession { flocks, pigeons }` (both `Signal<HashMap<...>>`) as a client-side cache of fetched entities.
- `src/api/*` are the HTTP client functions (one file per resource, e.g. `pigeons.rs`, `flocks.rs`), all going through `fetch_json` in `src/api/helpers.rs` — a thin `web_sys`/`wasm_bindgen_futures` wrapper (not `reqwest`), always `credentials: include` so the Kratos session cookie rides along. API functions return `Option<T>` (fetch/parse failure just collapses to `None`, logged via `tracing::error!`) and, on success, write straight into the relevant `LocalSession` signal — callers re-read from context rather than the function's return value for cached fields.
- Config constants (`src/config.rs`: `KRATOS_BROWSER_URL`, `API_HOST`, `SESSION_COOKIE_NAME`) are baked in at **compile time** via `option_env!`, sourced from `.env.dev`/`.env.release` by `build.rs` (picks the file based on Cargo's `PROFILE`). To change these per-environment, edit the `.env.*` file, not `config.rs`.
- Ory Kratos self-service flows (login/registration/recovery/verification/settings) are driven by `ory-kratos-client-wasm`, rendered generically through `ory_form_builder`/`ory_error` components rather than bespoke forms per flow.
- `dx serve`/`dx build` are configured via `Dioxus.toml`; wrangler serves the built static assets in production (`fancier/wrangler.toml` points `[assets].directory` at the Dioxus release output).
- Most modals are native `<dialog>` elements toggled imperatively via `document::eval(...showModal()/close()...)` (e.g. `UpdatePigeonModal`, `EditShadowModal`). Modals that hold their own reset-sensitive state instead render conditionally from a signal in the parent (`if show_modal() { Modal { ... } }`), so opening always remounts the component fresh — `TokenReveal` (`views/pigeons.rs`, gated by `Signal<Option<(pigeon_id, token)>>`) and `DeletePigeonModal` (`views/pigeon.rs`, gated by `Signal<bool>`, the typed-name-to-confirm delete flow) both use this pattern rather than the native `<dialog>` one, since a stale `<dialog>` left open with prior input wouldn't reset on its own. `TokenReveal`'s `on_close` navigates to the new pigeon's detail route (added 2026-07-18, task #30) — creation now ends on the pigeon detail view instead of the list.
- **Telemetry graphs** (`views/pigeon.rs` area, added 2026-07-17): user-defined graph configs (which telemetry key(s), time range) persist in `localStorage`, not the backend — a graph is a client-side view over `GET /pigeons/:id/telemetry/history`. Renders Live/Empty/Preview states depending on whether history exists for the selected range; non-numeric telemetry keys (see dovecote's telemetry-forwarding note above) are excluded from the key picker entirely.
- **Device log viewer** (`components/log_viewer.rs`, added 2026-07-18, task #25): reads the base64 ring-buffer chunks from `GET /pigeons/:id/logs` and decodes/downloads them client-side as a `Blob` (`helpers/download.rs`, `web_sys` `atob` → object-URL anchor-click pattern) rather than server-side — the chunks are opaque Zephyr dictionary-encoded log data, decoded host-side by the `pigeon` repo's `log_parser.py`, not by `fancier` itself; this viewer's job is just getting the raw bytes to the user's machine intact.

- **WASM code-split investigated and rejected as unsafe** (task #10, 2026-07-22): Dioxus 0.7.9 / `dioxus-cli` 0.7.9 do have a real, built-in route-level code-split mechanism — enable the `wasm-split` feature on the `dioxus` dependency, pass `dx build`/`dx serve --wasm-split` (an "Experimental" CLI flag), and `dioxus-router`'s `Routable` derive automatically wraps *every* leaf route in a lazy loader + suspense boundary (`dioxus-router-macro`'s `RouteType::Leaf` codegen, gated by `dioxus_config_macros::maybe_wasm_split!`) — no manual `#[component(lazy)]` annotation needed, just a `SuspenseBoundary` ancestor (e.g. wrapping `Wrapper`'s `Outlet`). It builds cleanly and DOES shrink the initial bundle dramatically (measured: main chunk 3.56MB → 1.3MB raw / ~1.18MB → ~390KB gzip for the shared bundle, plus a small per-route chunk, e.g. ~78KB raw for a landing-page-sized route) and chunk files fetch correctly over the network (verified via CDP-driven headless Chromium, both direct-load and route-to-route). **However, it is not safe to ship**: for real (non-toy) page content it silently fails to render for an unpredictable subset of components — the split `.wasm` chunk fetches with a real HTTP 200, but the route's content never mounts (stays a bare `<!--placeholder-->`), with zero console errors, zero thrown exceptions, and no failed network requests to explain it. Bisected extensively against the actual `Index` route: a trivial route, `Home` alone (icons + `Link` + `Route` reference), and a handful of minimal single-file repro apps (2, then 21, synthetic routes, matching the exact `#[layout(Wrapper)] #[layout(AuthGuard)] ... #[end_layout]` structure) all rendered correctly — but `Features` (`partials/features.rs`, a deeper-nested icon grid, no `Link`/`Route` usage) reliably failed 100% of the time across multiple clean rebuilds, while `Home` reliably succeeded across multiple clean rebuilds. No root cause was found (suspected: a correctness bug in `wasm-split-cli`'s relocation-based call-graph reachability analysis, consistent with it being labeled "Experimental" — its own error strings reference parsing wasm relocations/`--emit-relocs`/DWARF debug info, a fragile foundation for arbitrary real-world Rust codegen). All changes from this investigation (the `wasm-split` feature flag, a `SuspenseBoundary` in `Wrapper`, `--wasm-split` in `scripts/build-release.sh`) were reverted — do not re-enable without a newer `dioxus-cli` release and a from-scratch re-verification of real page content (not just a toy route), not only a successful build.
- **SSG adopted for public pages** (task #42, 2026-07-23): unlike `wasm-split` (above), `dx build --ssg` is viable in dioxus-cli 0.7.9 and is now wired into `scripts/build-release.sh`. What `--ssg` actually requires turned out to be a full Dioxus **fullstack** build, not a web-only flag: `dioxus/fullstack` + a crate-local `server = ["dioxus/server"]` feature (`Cargo.toml`), a `#[server(endpoint = "static_routes")]` fn in `lib.rs` returning `Route::static_routes()` (dx's CLI calls this exact endpoint name to discover what to prerender), and `main.rs` rebuilt around `dioxus::LaunchBuilder` + `server_only! { ServeConfig::builder().incremental(dioxus_server::IncrementalRendererConfig::new().static_dir(...)) }` so the server-only config compiles to nothing on the plain wasm/web build. `dx build --ssg` then compiles a *second*, native "server" target purely to drive the prerender at build time — spins up a real HTTP server on `127.0.0.1:9999`, renders every route `Route::static_routes()` returns (this already filters out anything with a `:dynamic` or `:..catch_all` segment — no manual route-list needed), and writes each as `public/<route>/index.html`. That server binary is never shipped or run in production; wrangler only ever serves the resulting static files (since the markdown-negotiation change below, through a thin `main` worker on the negotiable page routes; every other path is still direct `[assets]` serving). Confirmed empirically, not just build-success: raw HTTP responses (`curl`, no JS) now carry real page text for every public route — landing-page `index.html` went from a 611-byte empty shell to ~58.7KB with the actual hero copy, feature descriptions, and pricing text present pre-JS. Auth-gated routes (`/dashboard`, `/flocks`, `/session`, `/settings`) are also in `static_routes()` (dioxus-router's filter is about dynamic segments, not the `AuthGuard` layout) and DO get prerendered, but harmlessly: `Session`'s state `Signal` starts at `AuthState::Pending`, the client-only cookie check lives in a `use_future` that never runs/resolves during the synchronous SSG render pass, so every auth-gated page prerenders as `AuthGuard`'s "Verifying session..." placeholder wrapped in the real header/footer chrome — no private data, confirmed by inspecting the actual prerendered HTML. Hydration was verified clean via Playwright-driven headless Chromium (not just "the build succeeded" — this is exactly the rigor that would have caught task #10 sooner): zero console errors and zero page errors across `/`, `/features/`, `/pricing/`, `/dashboard/` (client takes over from "Verifying session..." and correctly redirects to `/unauthorized` once the cookie check resolves), and even the awkward case of directly loading a genuine dynamic SPA route not covered by SSG (`/flocks/:id/pigeons/:id`) — wrangler's `not_found_handling = "single-page-application"` fallback now serves the *landing page's* prerendered HTML (real content, not an empty shell) for that request, so the client briefly hydrates against the wrong route's markup before its own router mounts the correct component; this produces a harmless flash of landing-page content, not a crash or console error, but is a real UX nit worth knowing about. **Wrangler static-hosting compatibility, verified against a real local `wrangler dev` run of the built output** (not `dx serve`'s own dev server): a route like `/features` (no trailing slash) 307-redirects to `/features/`, which then 200s serving `public/features/index.html` — this is wrangler's default `html_handling` behavior (auto-trailing-slash directory-index resolution), nothing project-specific had to be configured. Two pre-existing dx-cli relative-asset-path bugs (task #9's CSS-link bug, task #28's root-relative-href fix) turned out to affect **every** prerendered nested route's HTML, not just the top-level `index.html` — `build-release.sh`'s sed fix now runs over every `public/**/index.html`, not only the site root. Not deeply chased: a quick `dx serve --ssg --force-sequential` smoke test started cleanly (matches `README.md`'s existing dev instructions, which already carried `--ssg --force-sequential` from an earlier, never-completed attempt at this same feature — see git history on `perch`, this repo's pre-monorepo predecessor, commit "Update Kratos crate and use SSG") but an immediate `curl` against it 404'd ("dx is not currently serving a web app"), likely a dev-server startup race rather than a real defect — worth a from-scratch re-check before relying on SSG in the day-to-day `dx serve` loop, but irrelevant to the production build path this task actually verified.
- **SSG hydration silently drops URL query params — route props are stale on every full-page load (task #43, prod signup outage, fixed 2026-07-26)**: a prerendered page bakes the route it was rendered AS into `initial_dioxus_hydration_data` (decode the inline script in any built `public/<route>/index.html` to see it — `/registration?` with a null flow, `/session/local?state=false` since `bool` prerenders as `Default`), and on hydration the client restores THAT route instead of re-parsing `window.location`. `Route::from_str` handles these URLs fine (tests in `lib.rs`) — the router was ruled out; it's purely the hydrated initial route. Consequence: every Kratos browser-flow handoff (full-page 303 back to `?flow=<id>`, or `/session/local?state=true`) lost its query param in the prod artifact — registration silently looped back to a fresh empty form, and post-login the `state=false` branch tore down the just-created session hint. Fix: `helpers/url_query.rs::url_query_param` — the address bar is the source of truth for query-derived props on entry; the route prop is only an SSG-side fallback. **Any future route that reads a query param on initial load must do the same.** Also fixed in the same pass: the flow views' 410-expired arm used to `nav.replace(flow: None)` + render "Refreshing expired session…" forever (a `use_resource` future does not rerun on the post-replace rerender) — they now fall through and mint a fresh flow inline on 410/404/403. Verified via Playwright-driven headless Chromium against the real built artifact served by `wrangler dev` (not `dx serve`, which doesn't hydrate and can't reproduce any of this): register → verify (code entry AND email magic-link) → signed-in dashboard, plus bad-password error rendering.
- **Markdown content negotiation** (Cloudflare Agent Readiness, 2026-08-10): fancier is no longer `[assets]`-only — `wrangler.toml` wires `main = "worker/access-gate.mjs"` (the existing var-gated staging Access gate, inert in prod), which delegates to `worker/markdown.mjs`: a request whose `Accept` header *strictly prefers* `text/markdown` over `text/html` (real RFC 9110 q-value parsing; ties and browser Accept strings keep HTML) gets the page's build-generated `<route>/index.md` served as `text/markdown; charset=utf-8` + `Vary: Accept` + `x-markdown-tokens`; everything else passes through, with `Vary: Accept` added on page-like paths. `[assets].run_worker_first` is a scoped path list (both slash forms of every negotiable route), so `/assets/*`, `/wasm/*`, SPA fallbacks etc. keep zero-worker direct serving — **three places must stay in sync**: `fancier/page-meta.json`'s `pages` map (which `build-release.sh` reads to generate a minimal title/description/canonical `index.md` for every route lacking a real one; `/` ← llms.txt and `/api-reference/` ← docs/api.md remain the two real-prose variants), `wrangler.toml`'s `run_worker_first` list, and `public/_headers`' per-route `rel="alternate"` Link blocks. Variant existence is probed against ASSETS at request time (a miss falls into the SPA fallback and comes back `text/html`, so the probe checks Content-Type), never a route list in the worker. Verified live via `wrangler dev` curl matrix (negotiation, q-values, passthrough, `_headers` Link + immutable caching, SPA fallback, 1 beacon/page) and a clean Playwright hydration pass on `/`, `/features/`, `/pricing/`.
- **Kratos v26 + `use_continue_with_transitions` handoff is client-consumed**: a completed browser verification flow (`state: "passed_challenge"`) carries no `continue_with` array — just a success message and a manual "Continue" anchor node (`href` = the after-verification return URL). `helpers::continue_anchor_href` + the verification view auto-follow it so register → verify → signed-in needs zero manual clicks. Dev/prod parity note: production Kratos is **v26.2.0** — `infra/docker-compose.yml` and `schemas/kratos/kratos.yml` are pinned to match (were stale at v25.4).
- **An expired session signs the tab out instead of rendering an empty dashboard** (task #49, 2026-08-13): every `api/*` function collapses a failed request to `None`, so a 401 used to reach the views as "no flocks, no pigeons, no alerts" — indistinguishable from an account that genuinely owns nothing, and the exact shape of the `cookies.domain` outage described above. The shared `dispatch()` in `api/helpers.rs` now checks for **401 specifically** and calls `helpers::session_lost()` (clears the `LocalSession` caches, drops the `session_expiry` hint cookie, sets `Session.signed_out` + `AuthState::Unauthenticated`); `AuthGuard` then routes to `/login` with an explanatory alert rather than the bare `/unauthorized` page, stashing the interrupted path in `localStorage` (`pidgeiot.return_to.v1`, 30-min TTL, cleared on read — it has to outlive Kratos's full-page 303, so it can't be a `Signal`) for `SetSessionCookie` to resume after sign-in. **This makes 401 a cross-cutting signal: a dovecote route that answers 401 for any reason other than "the session no longer resolves" will silently sign dashboard users out.** dovecote currently uses 403 for ACL denials and 404 for the public demo routes, which is what makes the inference safe. Only a real 401 acts: a dropped connection fails the fetch promise before there is a status to read, and 403/500/502 fall through untouched (each verified live). **Proactive half**: `helpers::watch_session_expiry`, armed by a `use_resource` in `App` that reads `session.state` so it exists only while signed in, sleeps toward the hint cookie's own expiry and sends **no network traffic** — the hint cookie is fancier's own (`write_session_hint_cookie`), not Kratos's, so unlike `ory_kratos_session` (HttpOnly) its value is readable and is the expiry. Each sleep is capped at 60s because browser timers don't count suspend time, so one long timer can outlive the session it guards. Known, deliberate gap: a session revoked server-side *before* its expiry is invisible to the watcher — the tab stays optimistic until its next request, which `session_lost` catches, and the graph/log viewers' existing polling makes that near-immediate on the pages that show live data. Closing it properly would mean a periodic `whoami` on every page. SSG-safe by construction: all of it hangs off `AuthState`, which stays `Pending` through the synchronous prerender, so the auth-gated routes still prerender as "Verifying session..." and the notice never lands in `login/index.html` (both confirmed against the built artifact). `views/flocks.rs` gained a matching `FlocksUnavailableState` for the *non*-401 case, so a 500 also stops masquerading as an empty account.

## Conventions worth knowing

- **Every `section` in `fancier` carries an `id`.** Two reasons, both load-bearing: it makes any part of a page linkable (`/pricing/#pricing-faq`), and it gives a section a name to refer to in conversation, so "section `demo-charts` needs this edit" beats describing a position on a page. Rules: kebab-case, named for what the section *is* rather than where it sits (`pricing-faq`, never `pricing-section-4`); prefixed with the page it belongs to, which both keeps ids unique and makes them self-describing out of context. Uniqueness must hold for the *rendered document*, not the source file — the landing page composes several `partials/*`, so those must not collide with each other or with `views/index.rs`, and anything rendered on every page (navbar, footer) needs an id that is safe everywhere. Treat an id as a public URL surface once it ships: renaming one breaks any link that points at it. **The convention is forward-only for exactly that reason** — around twenty ids predate it and are camelCase and unprefixed (`pigeonInfo`, `flockTelemetryGraphs`, `dashboard`). They stay as they are. The resulting mixture is deliberate, not drift, and "tidying" it would break links to buy consistency. If a case for renaming one ever comes up, the distinction that matters is public versus authenticated: nobody outside can deep-link into a page behind the login, so those carry no external breakage risk, while anything on a marketing page does.

- 2-space indentation (`rustfmt.toml`), consistent across all crates.
- **Panic and `expect` messages must never interpolate user or device data.** A production panic's message is captured by fancier's panic hook, stored as an error-report exemplar, and excerpted into an ops email — `capsules::normalize_message` redacts id/email/token-shaped substrings as the enforcing control, but prose it can't recognize survives, so the message itself must only ever describe the code's own state ("shadow version missing"), never a value from a user, a device, or a request body.
- No `?`-based early return inside the Worker route closures in `dovecote/src/lib.rs` — use explicit `let Ok(x) = ... else { return ... }` so failures always produce a CORS-wrapped error `Response` rather than silently 500ing through the framework's generic error path.
- Every response returned from the top-level router must call `.with_cors(&cors)`, where `cors` is that route's own `build_cors(&ctx.env, &req)` result (see `dovecote` architecture notes above) — there is no shared/global CORS instance to reference.
- DB sync from a Durable Object back to Postgres is always best-effort/fire-and-log (`console_error!`), never blocking or failing the primary request.
